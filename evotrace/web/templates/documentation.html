Research Documentation & Architecture

Problem formulation, system components, algorithm specifications, and design boundaries.

1. Research Problem & Positioning

Research Question

"Can provenance-aware modeling of document-level schema transformations help identify their impact on stored data and registered application queries while enabling safe recovery of supported transformations?"

Schema-flexible document databases like MongoDB empower agile application evolution by eliminating mandatory DDL migrations. However, implicit schema divergence creates significant operational challenges: document heterogeneity accumulates over time, legacy queries silently receive unexpected types or missing fields, and reverting schema mutations typically requires costly out-of-band backups.

Positioning & Boundaries: NoSQL-EvoTrace is an academic research prototype. Schema evolution, provenance logging, versioning, and database migration are individually established concepts. The contribution of this system lies in the unified integration of observed document-schema profiling, field-level append-only provenance, transparent query impact analysis with static and empirical checks, and conflict-checked recovery that preserves subsequent document edits.

2. Architectural Components

The system is organized into modular packages coordinated by Flask and PyMongo:

1. Schema Analysis Engine (evotrace.schema)

Discovers hierarchical paths across collections, computes observed type distributions, distinguishes absent fields from explicit nulls, and generates deterministic SHA-256 fingerprints.

2. Evolution Engine (evotrace.evolution)

Validates syntax, detects parent-child collisions, produces dry-run previews, executes transformations safely, and coordinates compensating rollbacks upon failure.

3. Provenance Engine (evotrace.provenance)

Maintains an append-only log of document field state transitions, pre/post fingerprints, and schema-version links for every executed mutation.

4. Impact Analyzer (evotrace.impact)

Evaluates registered application queries against modified paths using ancestor/descendant intersection rules and empirical execution deltas.

5. Recovery Engine (evotrace.recovery)

Synthesizes exact inverse operations. Checks current document state against recorded post-operation fingerprints to avoid overwriting downstream edits.

6. Evaluation Suite (evotrace.evaluation)

Runs reproducible experiments across configurable dataset sizes against synthetic ground truth, measuring F1, accuracy, latency, and overhead.

3. Algorithmic Specifications

Algorithm 1: Conflict-Aware Recovery Inversion

Input: Operation ID OP, Current Collection C, Provenance Record P
Output: Restored Documents Count, Skipped Conflict Count
1. For each doc_change in P.field_changes:
    a. doc ← C.find_one({"_id": doc_change.doc_id})
    b. If doc does not exist: record deletion conflict & continue
    c. curr_val, curr_exists ← get_nested_path(doc, target_path)
    d. curr_fp ← compute_fingerprint(curr_val, curr_exists)
    e. If curr_fp ≠ doc_change.post_state.fingerprint:
        Record conflict & skip document (preserves downstream modifications)
    f. Else:
        Restore exact pre-operation state (unset if absent, None if explicit null, or value)
        Append doc_change.doc_id to restored_doc_ids
2. Record append-only Recovery Provenance Event referencing OP

Algorithm 2: Static Query Dependency Intersection

Input: Proposed Operation Path Target_Path, Registered Query Catalog Q
Output: Set of Query Classifications and Severity Ratings
1. For each query q in Q:
    For each referenced path p_q in q.referenced_paths:
        If p_q == Target_Path: Return HIGH RISK (Direct predicate path alteration)
        If IsAncestor(Target_Path, p_q): Return HIGH RISK (Parent structure modified/removed)
        If IsDescendant(Target_Path, p_q): Return MEDIUM RISK (Child attribute mutated)
    Return LIKELY UNAFFECTED (Disjoint paths)
4. Assumptions and System Limitations

• Query Registration Model: EvoTrace inspects registered declarative MongoDB filters. It does not perform general static analysis of arbitrary host application code (e.g. dynamic SQL/BSON builders in third-party services).

• Scope of Safe Inverses: Safe type conversion is strictly validated and limited to non-lossy conversions (e.g., integer strings, whole-number floats, ISO datetimes). Lossy coercions (e.g., float with fractional part to integer) are intentionally rejected.

• Transaction Model: Multi-document atomic transactions require a MongoDB replica set or sharded cluster. In standalone or mock deployments, EvoTrace transparently falls back to safe operation journaling with compensating rollbacks.
